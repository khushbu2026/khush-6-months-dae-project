Issue 01 · Claude Desktop Sidestepped

The core constraint — Claude Desktop needs HTTPS, n8n only gives HTTP

n8n's MCP address is http://localhost:5678/mcp-server/http. Claude Desktop's "Add custom connector" screen only accepts https:// URLs.

Plain English

Claude Desktop's point-and-click connector form has a rule: the address has to start with the secure https://, not plain http://. n8n, running locally, only speaks plain http:// out of the box — two systems with a mismatched requirement.

Technical

This restriction lives specifically in Claude Desktop's OAuth-capable "remote connector" GUI, which assumes a publicly reachable, TLS-terminated endpoint — OAuth redirects and dynamic client registration are built for the public web. It is not a restriction on Claude Desktop's underlying MCP client in general, only on that one GUI flow.

How it was resolved

We ultimately bypassed this constraint entirely (see Issue 6) by using Claude Desktop's config-file server format instead of the GUI connector — it talks to http://localhost directly, no HTTPS required at all. The tunnel work below turned out to be unnecessary for the final solution.

Self-diagnose next time

If a GUI only accepts https:// for something running on your own machine, check for a config-file / CLI path that skips that GUI before building tunnel infrastructure.

Issue 02 · macOS / Homebrew Resolved

Homebrew was broken — permissions

Error: The following directories are not writable by your user:
  /opt/homebrew /opt/homebrew/Cellar /opt/homebrew/Frameworks ...
Plain English

brew install needs to write files into a shared system folder, and this Mac user account wasn't allowed to write there anymore.

Technical

Homebrew's /opt/homebrew prefix is normally owned by the installing user. Ownership had drifted — commonly caused by a prior sudo brew … call — so the directories were no longer writable by the current user. Homebrew's own suggested fix is sudo chown -R $(whoami) /opt/homebrew ….

How it was resolved

We didn't run the suggested chown — unnecessary system-wide ownership changes weren't worth it for one tool. Docker Desktop was already running, so cloudflared (and later ngrok) ran as Docker containers instead. Same result, zero permission changes.

Self-diagnose next time

If brew install fails on permissions and you don't want to touch system ownership, check for an official Docker image of the tool first.

Issue 03 · Docker networking Resolved

Containers couldn't reach "localhost" on the Mac

Pointing cloudflared/ngrok at http://localhost:5678 failed — they needed http://host.docker.internal:5678 instead.

Plain English

Inside a Docker container, "localhost" means the container itself, not your Mac. Containers are like separate little computers — "localhost" inside one doesn't reach anything on your Mac or in a sibling container. Docker Desktop provides a special hostname, host.docker.internal, that means "the actual Mac this is running on."

Technical

Each container gets its own network namespace; localhost/127.0.0.1 inside one resolves to that container's own loopback interface. Docker Desktop for Mac injects a DNS entry, host.docker.internal, resolving to the host — letting a container reach services published on the host or in sibling containers via their host-published ports.

How it was resolved

Every container that needed to reach n8n (cloudflared, ngrok), or that n8n needed to reach (Wazuh Indexer, Wazuh Manager API), used host.docker.internal instead of localhost.

Self-diagnose next time

If one container needs to talk to something on the host or in another container and localhost gives connection refused, try host.docker.internal first.

Issue 04 · Cloudflare / ngrok Resolved

Free tunnel URLs aren't stable

A Cloudflare "quick tunnel" gives a working HTTPS URL immediately, but the subdomain regenerates randomly every restart — no way to pin it without owning a domain.

Plain English

The free instant tunnel is like a temporary phone number — great for a quick call, useless if people need to reach the same number tomorrow.

Technical

Cloudflare "quick tunnels" (cloudflared tunnel --url … with no named tunnel) are anonymous and ephemeral by design — Cloudflare won't let you reserve a fixed hostname without owning a zone (domain) in your account, since the hostname is a DNS record under that zone. A named tunnel needs that domain. ngrok, by contrast, offers one free static domain per account with no domain-ownership requirement.

How it was resolved

Moved from Cloudflare's quick tunnel to ngrok, reserving a permanent free subdomain tied to the ngrok account instead of a domain that would need to be owned outright.

Self-diagnose next time

If a tunnel URL needs to stay fixed, check whether the tool requires domain ownership (Cloudflare named tunnels do) before starting — ngrok's free static domain is the lower-friction option without one.

Issue 05 · n8n · MCP auth Abandoned path

n8n's OAuth "sign-in service" failed to register Claude Desktop

Couldn't register with n8n's sign-in service. You can try again, or add
an OAuth Client ID in the connector settings.
Reference: "ofid_e916c1f7e2f08f19"
Plain English

n8n offered to let Claude Desktop log in automatically — like "Sign in with Google" — but the handshake that sets that up failed on n8n's side.

Technical

n8n's "Instance-level MCP" preview feature can require OAuth 2.1, including Dynamic Client Registration (RFC 7591) — the connecting client registers itself with the server's OAuth endpoint at connection time, with no pre-shared app credentials. This flow is primarily built and tested for n8n's own hosted cloud OAuth service; on a self-hosted instance, that registration step doesn't reliably complete.

How it was resolved

Abandoned the OAuth path entirely. Switched n8n's MCP auth to Access Token mode — a static bearer token — then connected Claude Desktop using that token through a different mechanism (Issues 6–7) instead of the GUI's OAuth flow.

Self-diagnose next time

If a self-hosted tool's OAuth "auto sign-in" fails with a registration error, check for a plain static API-token mode as an alternative — self-hosted OAuth servers are often less reliable here than a hosted SaaS equivalent.

Issue 06 · Claude Desktop config Abandoned path

First fix attempt also failed — unsupported config schema

Some MCP servers couldn't be loaded.
The following entries in claude_desktop_config.json are not valid MCP
server configurations and were skipped: n8n-mcp
Plain English

We tried editing Claude Desktop's settings file directly, using a newer format, to add the server with the access token. That Claude Desktop build didn't recognize the format and silently skipped the entry.

Technical

The first attempt used {"type": "http", "url": "...", "headers": {...}} — a newer addition to the config schema for remote HTTP servers with custom headers, not yet rolled out to every build. The older, universally-supported schema is {"command": "...", "args": [...], "env": {...}} — a local process Claude Desktop spawns and talks to over stdio.

How it was resolved

Switched to the older command/args/env format, using a bridge tool (mcp-remote, Issue 7) that runs as a local process and internally makes the HTTP call with the Authorization header — Claude Desktop never has to understand "type": "http" at all.

Self-diagnose next time

If Claude Desktop silently skips an MCP entry with a "not valid configuration" popup, suspect a schema-version mismatch — check your build against the docs, or fall back to command/args/env, the most universally supported format.

Issue 07 · macOS / Node Resolved

The real fix needed Node.js, and it wasn't installed

/bin/bash: node: command not found
/bin/bash: npx: command not found
Plain English

The bridge tool that finally worked (mcp-remote) is a small JavaScript program. Running any JavaScript program from the command line needs Node.js first, and this Mac didn't have it yet.

Technical

npx is Node's package runner — it downloads and runs an npm package on demand, but ships as part of Node itself, so Node has to exist first. mcp-remote is a small stdio↔HTTP proxy: Claude Desktop spawns it as a normal local process, satisfying Issue 6's schema requirement, and internally it opens an HTTP connection to n8n carrying whatever headers it's given (here, Authorization: Bearer <token>).

How it was resolved

Installed Node via nvm (no sudo/Homebrew needed) as a first pass; a system-wide install via the official installer (/usr/local/bin/node) followed separately and is what the final config points at — a more stable path than an nvm version-numbered one. Verified it worked by running mcp-remote manually for a few seconds and confirming Connected to remote server using StreamableHTTPClientTransport in its log, before wiring it into the real config — catching any auth/URL problems before burning a Claude Desktop restart cycle.

Self-diagnose next time

command not found for node/npx always means Node isn't installed, or isn't on the PATH whatever's calling it uses. Check with which node.

Issue 08 · mcp-remote Avoided

A silent trap in mcp-remote's header syntax

Plain English

There's a known bug where, on some platforms, an auth header value with a space in it (like Bearer abc123) can get mangled when passed as a command-line argument, silently breaking the header. This one was sidestepped before it ever caused a problem.

Technical

Cursor, Codex-CLI, and Claude Desktop (Windows) have a documented bug where spaces inside a spawned process's arguments aren't escaped correctly when the parent invokes npx. The workaround: keep the --header argument itself space-free (Authorization:${VAR}, no space around the colon) and put the actual value — which does contain a space — into an environment variable referenced by ${VAR}, since env vars aren't subject to the same mangling.

How it was resolved

Written this way from the start: "--header", "Authorization:${N8N_MCP_AUTH}" with "env": {"N8N_MCP_AUTH": "Bearer <token>"}, rather than embedding the full header inline.

Self-diagnose next time

If a bearer-token header mysteriously fails when passed as a CLI argument but works fine via curl, suspect argument-space-mangling — move the value into an environment variable.

Issue 09 · git Caught in time

git add . nearly staged your entire Mac

git status revealed /Users/Adult itself is a git repo. A plain git add . there would have staged everything: shell history, .claude.json (session/credential data), .docker/, .npm/, all of Library/, Documents/, Downloads/ — and the n8n access token just written into claude_desktop_config.json.

Plain English

The whole user folder, not just a project folder, turned out to be tracked by git. Typing the everyday shortcut "stage everything" there would have swept shell history and saved secrets right along with any real project files.

Technical

git add . stages every changed/untracked file under the current directory recursively, filtered only by .gitignore. Since the repo root was /Users/Adult, "current directory" was the entire home folder. git status --porcelain was run first, specifically to enumerate what would be staged before running any add.

How it was resolved

The command was never run. The full file list was surfaced instead, and the task paused for clarification — it turned out the ask had moved to a different task, so nothing was ever staged.

Self-diagnose next time

Before any git add -A or git add ., run git rev-parse --show-toplevel to confirm the repo root is what you think it is, and git status to see what's actually about to be staged — especially in a directory you didn't set up yourself.

Issue 10 · Wazuh Resolved

Wrong Wazuh account used — 401 Unauthorized on the Manager API

Indexer (:9200) with admin/SecretPassword → works.
Manager API (:55000) with admin/SecretPassword →
{"title":"Unauthorized","detail":"Invalid credentials"}
Plain English

Wazuh isn't one login for everything — the dashboard/search side and the "management" side use two completely separate accounts. The assumption that they matched was wrong.

Technical

A Wazuh deployment has at least two distinct auth surfaces: the Wazuh Indexer (an OpenSearch fork, port 9200, secured by OpenSearch Security with its own admin user) and the Wazuh Manager REST API (port 55000, secured by its own RBAC system with a separate service account — commonly wazuh-wui, with an auto-generated password). Both use HTTP Basic Auth and look similar, but are unrelated credential stores. The correct password was found by reading the Wazuh Manager container's environment variables (API_USERNAME, API_PASSWORD), set at deploy time.

How it was resolved

Located the actual API_USERNAME=wazuh-wui / API_PASSWORD=… pair from the manager container's environment, and confirmed it with a direct curl -X POST https://localhost:55000/security/user/authenticate test before wiring it into n8n as a credential separate from the Indexer's.

Self-diagnose next time

If Wazuh Indexer (9200) accepts your admin login but the Manager API (55000) rejects the same login, don't assume it's one account — check the manager container's env (API_USERNAME/API_PASSWORD) or your deployment's .env/compose file for a separate API service account.

Issue 11 · n8n CLI Resolved

n8n credential import failed on a missing ID field

SQLITE_CONSTRAINT: NOT NULL constraint failed: credentials_entity.id
Plain English

We tried to create a login entry in n8n by feeding it a file directly instead of using the web form, and n8n's database rejected it because we hadn't given it a required internal ID.

Technical

n8n import:credentials writes rows directly into n8n's database (SQLite here). Creating a credential via the web UI auto-generates a unique id; the CLI importer does not — it expects the JSON to already include one, and SQLite's NOT NULL constraint on that column rejects the insert otherwise.

How it was resolved

Generated random 16-character alphanumeric IDs, matching n8n's own style, and included them explicitly in the credential JSON before importing — the second attempt succeeded.

Self-diagnose next time

A NOT NULL constraint failed on an id column from a CLI import tool almost always means: include an explicit unique ID in the record — the CLI skips whatever auto-generation the GUI does for you.

Issue 12 · n8n CLI Worked around

n8n's own CLI test-runner conflicted with the running server

n8n Task Broker's port 5679 is already in use.
Do you have another instance of n8n running already?
Plain English

We tried to test-run a workflow from the command line, inside the same container where n8n was already running as a live server — and the test command tried to start its own helper process on a port the live server already held.

Technical

n8n execute --id=… spins up n8n's Task Broker — an internal component for scaling task execution — on a fixed local port (5679) as part of a one-off CLI run. The container's main n8n start process was already holding that port, so the second process couldn't bind it and failed immediately.

How it was resolved

Abandoned CLI-based execution for this container and tested through the n8n web UI instead — which is why a temporary manual-trigger test branch (a harmless fake IP and a non-existent agent ID) was added directly to the workflow, safely testable by clicking "Execute" in the browser.

Self-diagnose next time

n8n execute and a running n8n start server can't share one container. To test a workflow ad hoc, use the web UI's Execute button, or run the CLI in a separate n8n instance that isn't also running the server.

Glossary

The recurring concepts, so you're not re-deriving them from context every time.

MCP

The "language" Claude uses to call out to external tools, like n8n's workflows.

Model Context Protocol — a standard for exposing tools/resources to an LLM client over stdio or HTTP.

stdio vs. HTTP transport

stdio = a program running right next to Claude it talks to directly. HTTP = a separate server elsewhere Claude talks to over the network.

stdio: parent spawns a child, communicates over stdin/stdout. HTTP: client makes network requests to a URL. mcp-remote bridges the two.

host.docker.internal

The special address a container uses to mean "the Mac it's running on."

A DNS name Docker Desktop resolves to the host's (or bridge gateway's) address, for container→host/sibling-container traffic.

OAuth 2.1 / Dynamic Client Registration

"Sign in automatically" — but for two programs to do that safely, one first has to formally register itself with the other.

RFC 7591: a client registers itself with an authorization server at connection time, no pre-shared app ID needed.

Bearer token

A password-like secret string attached to a request to prove who you are — a wristband at an event.

A credential sent in the Authorization: Bearer <token> header; the server trusts whoever holds a valid token.

Wazuh Indexer vs. Manager API

Two different "departments" inside Wazuh with separate logins — one stores/searches alert data, the other lets you control the system.

Indexer (:9200): OpenSearch-based storage/search layer. Manager API (:55000): RBAC-secured REST control-plane, used here to trigger Active Response.

Active Response

Wazuh's built-in "take action automatically" feature — e.g. blocking an IP at the firewall on the affected machine.

A Manager API call (PUT /active-response) instructing a specific registered agent to run a predefined response script (here, firewall-drop0) against a target.

n8n Data Table

A small built-in spreadsheet-like table workflows use to remember state — e.g. which IPs are already blocked.

A first-class n8n entity queried/written by the n8n-nodes-base.dataTable node; not manageable via the CLI used this session.

Known gaps

Not errors — deliberately left unfinished, and why.

  • Grafana annotation step — needs a Grafana API key (header-auth credential); not configured, since no Grafana login was provided.
  • Email notification step — needs SMTP credentials; not configured, since none were provided. The workflow runs fine up to this point regardless.
  • blocked_ip_log Data Table — existence unverified; n8n's CLI doesn't expose Data Tables, and checking requires the web UI.
  • Auto-Block workflow is inactive on purpose — the 5-minute schedule trigger hasn't been turned on. It won't run automatically until activated in the n8n UI.
